Stillbrook — Password Policy (v4.2.1)

═══════════════════════════════════════════════════
SECTION 1 — GENERAL REQUIREMENTS
═══════════════════════════════════════════════════

- Minimum length: 12 characters
- Must contain: uppercase, lowercase, digit, special character
- No reuse of last 5 passwords
- No dictionary words or sequential patterns
- Passwords are case-sensitive

═══════════════════════════════════════════════════
SECTION 2 — DELIMITER ASSIGNMENT BY DEPARTMENT
═══════════════════════════════════════════════════

| Department       | Delimiter |
|------------------|-----------|
| General          | !         |
| Engineering      | !         |
| Finance          | #         |
| Operations       | #         |
| IT Admin         | #         |
| Service Account  | @         |

═══════════════════════════════════════════════════
SECTION 3 — PROJECT NAME RULES
═══════════════════════════════════════════════════

- Use the FULL initiative name, not the short code
- Multi-word project names use "_" as internal separator
  (e.g., "Phoenix_DR" not "PhoenixDR" or "Phoenix DR")
- Project name must match the project charter EXACTLY
- Onboarding accounts: format is <Project>_<Year>!

═══════════════════════════════════════════════════
SECTION 4 — OPERATIONS & IT ADMIN ACCOUNTS
═══════════════════════════════════════════════════

- Delimiter: "#"
- Format: <ProjectName>#<Year>
- Project identifier must match the project charter
  EXACTLY (including underscores)
- Admin accounts may share credentials with the
  project operations lead (known policy gap,
  under Q4 review)
- All login attempts on admin accounts are logged
  to the DR audit trail

═══════════════════════════════════════════════════
SECTION 5 — SERVICE ACCOUNTS
═══════════════════════════════════════════════════

- Delimiter: "@"
- Format: <ProjectName>Service@<Year>
- Project name MUST be PascalCase
  (no spaces, no underscores)
- The "Service" suffix is mandatory and is NOT part
  of the project name
- Rotation: 90 days (automated)
- No interactive login — service accounts use
  token-based auth only
- Service account inventory maintained by IT
  Operations. Refer to CMDB for active list.

═══════════════════════════════════════════════════
SECTION 6 — LOCKOUT & ACCOUNT DISABILITY
═══════════════════════════════════════════════════

- 5 failed attempts → 15-minute cooldown
- 3 cooldowns in 24h → account disabled,
  manual re-enable required by IT

═══════════════════════════════════════════════════
SECTION 7 — IDENTITY & ALIAS RULES
═══════════════════════════════════════════════════

Usernames are unique per department but NOT
unique across departments. The same individual
may hold accounts in multiple departments with
independent credentials.

Aliases are used across systems. The following
formats all refer to the same identity:

| System        | Format         |
|---------------|----------------|
| Email         | Full Name      |
| Teams Chat    | @handle        |
| Ticketing     | Initial. Last  |
| Audit Log     | first.last     |
| HR Portal     | Last, First    |
| Service Desk  | First L.       |

Correlate identity before determining department
context.

═══════════════════════════════════════════════════
SECTION 8 — CREDENTIAL CONSTRUCTION
═══════════════════════════════════════════════════

Credential construction follows departmental
standards defined in this document.

Refer to the relevant project charter for exact
project identifiers. Refer to HR department rosters
for account-to-department assignment.
